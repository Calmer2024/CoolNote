# 启动主题闪烁与切换不同步

## 复现及原因

1. 系统设置为深色，CoolNote 保存浅色后重启；反向配置也可复现。原 ThemeButton 总是以 system 初始化，在 useEffect 中先覆盖根节点主题，等 library 加载后再套用保存主题。回归测试捕获到 light → dark → light 和 dark → light → dark 的根节点变更。
2. index.html 没有首屏主题引导，CSS 默认浅色，原生窗口跟随系统，因而 React 接管前也可能先绘制不同的背景/窗口外观。
3. useNotes 在 Promise.all 和上次笔记恢复结束后才暴露 settings，列表/正文的耗时放大了临时主题的停留时间。
4. 各组件有 120～250ms 不等的颜色 transition；Mermaid 还将主题更新放进 220ms 的源码防抖计时器，导致图表滞后。
5. 修复加载顺序时发现额外竞态：初始化尚未结束时用户切换主题，初始化结果仍会回写旧 settings。新增测试先确认失败，再按 settingsRevision 排除旧结果。

## 修改

- 原生窗口在创建前读取原子写入的 library.json 中的主题，预先配置窗口主题；窗口先隐藏，页面加载完成后才显示，并在显示前设置正确的 WebView 背景。该读取不依赖笔记数据库的加载或迁移。
- 原生 initialization_script 将保存模式交给 index.html 的同步引导脚本。在样式、React 和数据请求之前确定 data-theme、color-scheme 和页面背景。浏览器环境采用上次确认保存的缓存；首次使用/无效值采用系统主题。
- 应用级 useThemeAppearance 管理全局主题，不再让按钮的初始 system 状态控制整个页面。主题设置与列表/正文分开就绪，旧设置版本不能覆盖新版本。
- 顶部按钮与设置页复用同一套立即预览、成功保存缓存、失败回退流程；跟随系统时监听系统外观，切到固定主题后移除监听。原生标题栏/背景也随之更新。
- 支持 View Transitions 的 WebView 使用统一的 180ms 页面淡变，切换期间关闭组件各自的 transition，并等待 Mermaid 新主题渲染完成后再显示新画面。Mermaid 的主题更新不再等待源码防抖。
- 尊重减少动态效果设置；不支持 View Transitions 时同步直接切换，避免各组件分批渐变。

## 验证

- 回归测试覆盖首屏引导（原生偏好优先于过期缓存、浅/深/系统模式）、延迟加载、保存成功与失败回退、缓存一致性、系统事件订阅/清理、快速反向切换、图表等待及旧 settingsRevision 竞态。
- Rust 测试覆盖启动时浅/深/系统模式及不存在、损坏、旧格式的配置回退。
- 完整前端构建和 Rust 测试通过。开发版窗口已成功启动；没有改动用户保存的主题设置。
- 隔离浏览器预览故意设置相反的缓存并延迟 800ms 交付设置，分别采样浅色、深色启动的 100 帧。样例只使用真实组件及样式，不写入用户笔记。
- 当前隔离浏览器不提供 View Transitions API，因此该环境实测的是直接切换分支；统一淡变分支通过自动测试验证等待、合并及取消顺序，桌面 WebView 的动画观感需在开发版验收。

## 桌面验收

1. 系统深色时，在 CoolNote 设置选择浅色，完全关闭后重开，第一屏及后续应始终浅色。系统浅色时重复深色测试。
2. 在笔记、小记、任务、画廊及设置页切换主题，观察页面是否统一变化；包含 Mermaid 的笔记中，图表不应额外延迟 220ms 更新。
3. 启动加载仍在进行时切换主题，加载完成后不应被旧主题覆盖；关闭再开应保持确认保存的选择。
4. 选择跟随系统，切换系统外观应响应；选择固定浅/深色后，系统外观变化不应覆盖选择。
5. 开启系统的减少动态效果选项，主题直接切换，不播放淡变动画。
