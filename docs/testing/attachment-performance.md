# CoolNote 附件与图片性能测试

## 目标

附件性能门禁用于验证大量图片、音视频、网页资源和普通附件存在时，笔记仍能保持可编辑、可保存、可恢复，并避免一次性读取或解码全部二进制资源。

附件元数据与附件内容是两个不同层级：列表接口只返回名称、类型、大小、哈希和标识；只有资源进入视口或用户执行播放、预览、下载时，才读取单个附件内容。

## 自动测试入口

```powershell
npm run perf:attachments
```

该命令依次执行：

- 前端千图编辑器压力测试；
- Rust 附件存储、读取、并发、异常输入和千图文档压力测试。

日常构建中的快速回归由以下命令覆盖：

```powershell
npm run test:editor
npm run check:editor-performance
```

## 数据规模与门限

| 场景 | 规模 | 门限或断言 |
|---|---:|---:|
| 附件元数据列表 | 2,000 条，共享 64KB 文件 | 150ms，列表不得携带二进制数据 |
| 单附件读取 | 64KB | 100ms |
| 并发附件读取 | 16 线程、共 400 次 | 2,000ms |
| 去重附件保存 | 500 条、每条 32KB | 2,000ms |
| 去重附件删除 | 500 条 | 2,000ms，最后引用删除后清理文件 |
| 千图文档保存 | 1,000 个轻量引用节点 | 500ms，文档 JSON 小于 250KB |
| 千图文档读取 | 1,000 个轻量引用节点 | 250ms |
| 千图编辑器挂载 | 1,000 个图片节点 | 5,000ms，零张离屏图片提前读取 |
| 千图文档单次编辑 | 1,000 个图片节点 | 500ms |

门限有意保留 CI 和不同硬件的波动空间；日常关注实际指标相较基线是否出现数量级回退。

## 稳定性场景

- 非法 Base64 必须被拒绝，不能产生数据库记录或文件；
- 单个附件超过 25MB 必须被拒绝；
- 附件文件缺失时，内容读取返回错误，但元数据列表仍然可用；
- 多个附件引用相同内容时只保存一份文件；
- 删除最后一个引用后清理共享文件；
- 批量导入最多同时处理三个文件，避免大量 FileReader、Base64 字符串和 IPC 请求同时占用内存；
- 旧笔记中的内嵌 Data URL 在规范化时自动转换为 `coolnote-attachment:` 轻量引用；
- 图片、音频、视频和 HTML 资源只在进入视口附近时加载，所有节点共享一个 `IntersectionObserver`。

## 性能架构

```text
文档 JSON
  └─ coolnote-attachment:<attachment-id> 轻量引用
                   │
                   ▼ 进入视口 / 播放 / 下载
          get_attachment_data(id)
                   │
                   ▼
          单个本地文件读取与 Data URL
```

禁止在附件列表、笔记初始载入或保存响应中返回全部 Base64 内容。新增附件相关功能时，应先扩展本门禁，再调整门限或实现。
